# Authored fixtures and Sandbox source

`FixtureService` stores immutable `FixtureSet` records in the portable `fixtures` collection. A set names one decision, one dataset, and an explicitly authored model identity. Each `FixtureBinding` names one case and retains the compiled request bytes, byte hash, compiler name and version, destination, and one authored answer or safe error. The record's content hash covers those binding identities and outcomes; a changed set requires a new set ID. Display name, note, and creation time do not affect the content hash.

`FixtureTransportFactory.for_case(case_id)` supplies the case context missing from the common `ProviderTransport.dispatch` signature. Dispatch checks the full compiled request and requires exact case, compiler, version, body bytes and hash, adapter, destination, and model identity. An unmatched request returns `not_sent` with `missing_fixture`; malformed requests return `not_sent` with `preflight_failed`. It never contacts a provider or substitutes another binding. Identical wire bodies may have different authored answers for different cases. The runner must check a set's decision and dataset IDs against its run source before using the factory.

Fixture profiles use adapter `fixture`, destination `fixture:jev-choice`, an `authored-` model identity, and no credential reference. Jev's live-profile validator remains separate. The fixture path validates generic normalized answers with the actual question and option IDs in each request. Probability distributions and authored confidence are optional; if present, probabilities must cover every option, sum to one within the named tolerance, and support the selected option. Missing probability, confidence, usage, and duration remain missing. This path does not reinterpret a generic answer as a Jev wire response.

`DemoService` takes a source factory, clock, and ID factory. It first validates the packaged `src/deykit/data/sandbox.json` corpus and prepares compiled bindings. It then creates a new project directory, saves the choice definition and revision, imports all twelve JSON cases in one source transaction without a decision context, saves nine separate `authored_fixture` labels in one batch, and stores a fixture profile and set. Importing without decision validation preserves `ex-011` as a visible case; selecting it against the full schema fails before compilation or dispatch. All binding requests are compiled from the validated selected state, while case records retain the complete input. The project path must not already exist, so user files are never overwritten.

The corpus translates authored design examples into portable source records. Its 12 cases, 11 valid inputs, 10 authored valid answers, one authored response error, and one invalid input are automated verification material. The resulting 6/8 labelled-answer calculation is **not** observed provider quality or a stored run/evaluation report. Running the demo through the later execution service will produce separate immutable run evidence tagged as fixture mode. No secret, credential, live inference, or timing evidence is included in the project.

The implementation relies on P02 source operation receipts and create-only immutable records, P03 decision revisions, P04 transactional import, and P05 label batch semantics. Storage source and index rebuilding are separate from fixture behavior; SQLite remains disposable. The current programmatic service is the P07 CLI adapter boundary, and the per-case factory is the P08 runner boundary.
